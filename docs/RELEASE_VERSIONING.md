# Release versioning

AnyTTY has one public release identity. The source of truth for a release is
the `VERSION` file; the GitHub tag is derived from it, for example:

```text
0.0.1-beta.12+17
```

The part before `+` is the public release version. The part after `+` is the
monotonically increasing mobile build number.

The following files must contain the matching version without the leading
`v` where their format requires it:

- `VERSION`: the only file edited for a new release.
- `package.json` and `package-lock.json`: generated by `make sync-version`.
- `clients/flutter/pubspec.yaml`: generated by `make sync-version`.

Run `make sync-version` after changing `VERSION`. The release workflow also
reads `VERSION` directly and passes the derived values to Flutter, so the
release build does not depend on a stale generated manifest.

The GitHub release workflow validates these values before producing CLI and
Android artifacts. Release asset names always use the complete tag, such as
`anytty-v0.0.1-beta.12-android-arm64-v8a.apk`.

## Store mapping

Android uses the Flutter values directly:

- `versionName`: the part before `+`, for example `0.0.1-beta.12`
- `versionCode`: the part after `+`, for example `17`

App Store Connect does not allow a new build to use a marketing version lower
than an existing version. The current iOS store record is `1.1.0`, so the
iOS representation of this release is `1.1.0 (17)`. The build number remains
the same as Android and the GitHub release; only the iOS marketing version is
different because of Apple's monotonic store constraint.
